# Adding a city

Everything city-specific is a TOML config; the pipeline core is city-agnostic.

Read `configs/staunton/staunton.toml` first. It's close to the smallest honest
config, and it's the one that has been run end to end, so its comments carry
what the run measured. `configs/chicago/chicago.toml` is the other end: it was
the validation corpus, so it declares nearly every optional key.

## 0. Pick the volume first

The best predictor of whether a town places well is **how little it has grown
since the edition was printed**. It matters more than a dense downtown, a
famous name, or a distinctive street pattern.

Matching searches modern centerlines for the intersections each sheet names, so
every modern street inside the search box that didn't exist in the printed year
is a chance to match the wrong one, and subdivision street names repeat.
Compare the town's census count in the edition's decade with its latest one.
Staunton grew 1.25x since 1950 and its box holds 174 centerline streets over
51 km². Crystal Lake grew 9.2x and its box holds 563 over 63 km², most of them
subdivision streets no sheet ever saw.

Four more filters, all answerable before any model spend:

- **A late edition**, closest to modern street names. The LOC collection
  endpoint answers a state-and-decade facet query in one request, with
  `resources[0].files` carrying each item's sheet count.
- **8 to 25 sheets.** Cheap to read, and enough that the two-pass scale and
  rotation medians have a population to work from.
- **One printed scale.** Fetch sheet 1 and read the key map's scale statement.
  A book binding two scales needs the `page_scale_multiples` exemption in §4,
  which is an owner decision.
- **A street grid near the cardinals.** The default prompt asks the reader for
  `horizontal|vertical` and nothing else, so a diagonal street's label gets a
  cardinal axis and the pixel corner it forms isn't the corner the sheet draws.
  Fetch the box's centerlines (`scripts/fetch_osm_centerlines.py`) and take the
  length-weighted share of named meters whose local bearing is more than 15°
  off the nearest cardinal, over every feature touching the box. No command
  prints it yet.

  | City               | Named km | Within 5° | Over 15° off | Placement error |
  | ------------------ | -------- | --------- | ------------ | --------------- |
  | Chicago            | 7,180    | 83.8%     | 12.3%        | 1.2 to 3.0 m    |
  | Cleveland SE probe | 584      | 72.2%     | 19.2%        | about 10 m      |
  | Staunton           | 142      | 73.7%     | 18.7%        | about 2 m       |
  | Crystal Lake       | 354      | 54.3%     | 30.3%        | 114 to 122 m    |

  Three under 20% place; the one at 30% doesn't. That's a rule of thumb off
  four cities. Nothing gates on it, and nobody has measured where between 19%
  and 30% a town stops placing. Chicago's row is the whole reference file
  rather than one volume's box, so read it as the large-city control.

Then read the street names off the key map and confirm they resolve in OSM over
the box you're about to declare. That's go/no-go, not a coverage figure: by eye
you find the big labels and miss the ones that will actually fail. Staunton's
sample scored 37 of 37 where the annotator's own read of the same sheet
resolves 50 of 56. The number that means something is
`work/<volume>/name-match.json` after the run.

Read the key map's marginal notes for detached areas too. §4 says why.

## 1. The minimal config

```toml
[city]
name = "Springfield, Ill."            # also drives cache-file naming
loc_query = "sanborn02163"            # narrow: see below
aliases_dir = "aliases"               # historical->modern renames, per volume
evidence_channels = ["junction"]      # verified accept is opt-in; default is none
annotation_model = "codex:gpt-5.6-terra"   # omit for the built-in default
```

That's a complete, runnable city. With no `centerlines` key, OSM is the
default: `autogeoref run` materializes
`cache/osm-centerlines-<city-slug>.geojson` beside the config with one polite
Overpass fetch per uncovered volume bbox, cached forever.
`scripts/fetch_osm_centerlines.py` warms it offline.

**Keep `loc_query` narrow, ideally one page.** `autogeoref discover` paginates
`loc.gov/search`, which starts timing out a few pages in. `"sanborn maps
staunton illinois"` matches 9,358 records and died on page 5 of 10. Use the
volume-family identifier instead: the `sanborn<NNNNN>` prefix shared by every
edition of one town, read off any item id. `"sanborn02165"` returns exactly the
seven Staunton editions in one page. Check what you wrote; neighboring prefixes
are other states.

**Omitting `annotation_model` gives the built-in default**, which routes to a
different CLI from the one the worked example uses. The prefix picks the
provider; the README's model tables say which need an executable on `PATH` and
which need an API key.

**`evidence_channels` is empty by default and nothing warns.** Strict, rescue,
and corroboration still run, but no sheet can reach a verified accept with no
channel to vote. Declare only channels your data can feed: `"addresses"` needs
the ranges §2 describes, which OSM doesn't have.

**What the OSM default gives you.** Street names and geometry, so name matching
and the junction channel both work. Overpass carries no node ids, so the
converter derives the intersection graph from vertices two different streets
share. Measured against Chicago's official centerlines, 94% of derived nodes
land within 20 m of a real one (median 1.3 m), recovering about two thirds of
them. No address ranges, so the addresses channel abstains. The cache records a
`schema_version` and re-derives in place when it changes, so an offline
machine's prefetched copy keeps working.

## 2. Bring your own centerlines

```toml
centerlines = "reference/city_centerlines.geojson"   # used verbatim, never written
centerline_name_property = "street_nam"
centerline_type_property = "street_typ"
```

- **Name and type properties** (configurable, above). Name is the bare
  uppercase street name without direction or type (`MADISON`); type is an
  abbreviated code (`ST`/`AVE`/`PL`/…). The type code matters for numbered
  PLACE/COURT twins, since `31ST PL` is a different street half a block from
  `31ST ST`.
- **Address ranges** (optional, fixed names): `l_f_add`/`l_t_add`,
  `r_f_add`/`r_t_add`. These power the addresses channel. Without them it
  abstains and verified accept runs on corroboration and junction only.
- **Intersection topology** (fixed names, required by the junction channel):
  `fnode_id` and `tnode_id`. Any hashable value works; what matters is that two
  features meeting at an intersection carry the same id there. A node is an
  intersection when three or more feature _ends_ meet, or two do under
  different names. A file whose features aren't split at intersections supplies
  no interior nodes, so prefer a source noded per block. Omit these with the
  channel declared and it fails quietly: it records `skipped: centerline world
has no intersection nodes` on every page and verified accept runs on
  corroboration alone.

### 2a. Getting a file

A city open-data portal is best when one exists. When it doesn't, for any US
city the Census Bureau's **TIGER/Line ADDRFEAT** shapefile satisfies both
halves of §2 from one free download per county. Its edges are split at every
intersection and carry address ranges.

```sh
# one file per county FIPS; McHenry County, Illinois is 17111
curl -O https://www2.census.gov/geo/tiger/TIGER2024/ADDRFEAT/tl_2024_17111_addrfeat.zip
```

| ADDRFEAT            | §2 property                 | Note                                                  |
| ------------------- | --------------------------- | ----------------------------------------------------- |
| `FULLNAME`          | `street_nam` + `street_typ` | split it the way `autogeoref.osm.split_osm_name` does |
| `LFROMHN` / `LTOHN` | `l_f_add` / `l_t_add`       | left frontage range                                   |
| `RFROMHN` / `RTOHN` | `r_f_add` / `r_t_add`       | right frontage range                                  |
| edge endpoints      | `fnode_id` / `tnode_id`     | round each endpoint coordinate and key on it          |

Endpoint keying is enough here, unlike OSM, because TIGER edges are already
split at intersections. On the McHenry file clipped to Crystal Lake's
`bounds_bbox`: 2,242 usable named edges, 578 names, every one carrying at least
one frontage range, 1,030 junction nodes. Against OSM over the same box: 1,056
named ways, 561 names, no ranges, 1,075 derived nodes. **TIGER doesn't buy a
better junction graph, it buys the addresses channel.**

Four caveats: it's modern geometry, so streets that no longer exist are absent;
it's NAD83 (EPSG:4269), which is below this pipeline's tolerances so needs no
reprojection; the ranges are Census ranges rather than parcel truth; and a
one-sided range makes the addresses channel abstain on the other frontage,
never refute.

### 2b. Chicago's own data

Both files `configs/chicago/chicago.toml` points at are gitignored. Both are
City of Chicago open data, exported as GeoJSON from the portal at
`https://data.cityofchicago.org/d/<id>`. "Export → GeoJSON" produces the field
names each key expects; §2's defaults are that dataset's own column names.

| Config key        | Dataset                                | Portal id   |
| ----------------- | -------------------------------------- | ----------- |
| `centerlines`     | Street Center Lines                    | `6imu-meau` |
| `community_areas` | Boundaries - Community Areas (current) | `cauq-8yn6` |

The whole file in both cases, no clip, roughly 76 MB and 2 MB. Neither is a
template for another city; §2a is.

## 3. Optional city data

```toml
community_areas = "reference/community_areas.geojson"  # named polygons for bounds_areas
rail_geojson = "reference/rail-overpass.json"          # rail rescue anchors
rail_gazetteer = "rail-gazetteer.json"                 # era-label -> rail-group bindings
renumbering_table = "renumbering-<city>-<year>.json"
address_block_size = 100                               # house numbers per block
loc_catalog = "loc-catalog-<city>.json"                # volume titles and years
```

**`loc_catalog` is what names a published layer.** It's a saved LOC search
response, and it's the only source of a volume's title, year, and number on its
_first_ publish. Without it a layer is titled by its bare identifier with a null
year and draws under a single `undated` chip. A later publish falls back to the
previous manifest, so the gap shows up once and then hides.

```sh
uv run autogeoref discover "<your loc_query>" --out configs/<city>/loc-catalog-<city>.json
```

**Don't fill a missing year by reading one off the sheets.** The example city
is the counterexample: `sanborn02165_007` is an April 1921 base carrying a
January 1948 paste-on index, so a plausible read answers 1921 where the
cataloging answer is 1948. Crystal Lake's `sanborn01810_007` is a 1936 base
under a 1955 revision.

The rest: `renumbering_table` matters when the city renumbered after some
volumes were printed (Chicago, 1909); keep a provenance file beside it.
`rail_geojson` and `rail_gazetteer` are all-or-nothing, and unbound labels
deliberately yield no candidates. `address_block_size` sets the addresses
channel's block tolerance (0.75 × block); 100 is the common US convention.

## 4. Per-volume knowledge

```toml
[volumes.sanborn12345_001]
bounds_bbox = [-89.68, 39.76, -89.61, 39.83]  # or bounds_from / bounds_areas
scale_m_per_px = 0.067                         # omit both to derive two-pass
rotation_deg = 1.1
addresses_modern = true                        # tri-state, see below
page_scale_multiples = { cbd1 = 4.0 }          # rare
```

### Bounds

Priority: `bounds_bbox` > `bounds_from` (a counterpart volume's footprint) >
`bounds_areas` (community-area union). Declare none and a box is derived from a
sampled read.

**Bounds is a hard filter and `bounds_bbox` is the one source with no slack.**
The index drops every centerline outside the box, so a street the box excludes
is a candidate for no sheet in the volume, and the sheets naming it reject with
zero candidates and no diagnosis. The other sources are padded (0.01°; the
derived path 0.02/0.015). Draw it around the streets the sheets name, not
around the key map's neat outline, and give it margin yourself. Six Chicago
volumes were clipped this way and cost 58 sheets between them; each one's
stanza in `configs/chicago/chicago.toml` says which edge was wrong and why.

**Read the key map's marginal notes before drawing the box.** A volume's
footprint isn't its town. A sheet often covers a works, a quarry, or a station
miles outside the built-up area, and the key map says so in the margin rather
than drawing it. Crystal Lake's reads "2 1/2 MI. TO AMERICAN TERRA COTTA CORP.
SHEET NO. 9". A box drawn around the town excludes that sheet with no
diagnosis, and no amount of checking downtown street names can catch it.

Never derive a box from human ground truth. A box drawn around hand-placed pins
lets those pins decide which sheets can place at all.

### Constants

Recorded `scale_m_per_px` / `rotation_deg` pin the volume gates. Omit them and
`stage_match` derives both from the two-pass medians and persists
`volume-constants.json`.

`scale_m_per_px` is **EPSG:3857 meters per full-res pixel**. Fit-sourced and
derived values are already in that frame. A pin computed from a printed scale
bar at scan DPI is true ground m/px and must be divided by cos(latitude) first,
about 1.34x at Chicago.

### `addresses_modern`

`true` means printed house numbers are today's. `false` means the volume
predates the city's renumbering and numbers convert through
`renumbering_table`. **Unset means modern, not unknown**, because most cities
never renumbered and the base case has to work with no config.

That default is safe with no `renumbering_table` and a hazard with one. If your
city renumbered, declare the era on every pre-renumbering volume. Left unset,
the printed numerals are read against today's grid, about 900 m off in
Chicago's case, and because the addresses channel is the only one permitted to
refute, the default doesn't merely fail to help: it vetoes correct sheets in
the confident language of evidence. The run policy refuses before work whenever
the addresses channel is enabled for a renumbering city and a volume declares
no era.

Don't guess the other way either. A wrong `true` on a pre-renumbering volume is
the measured Hermitage trap, producing confidently wrong placements. The engine
won't infer era from an edition year, which would bake one city's renumbering
calendar into every city.

### `page_scale_multiples`

Rare, and an owner-granted exemption from the volume-scale contract. A book
sometimes binds a sheet at a different scale: Chicago's Loop books each carry
two "Congested District" sheets at 200 ft to the inch against the book's 50.

Give the ratio as a **multiple of the volume's own measured scale**
(200/50 = `4.0`), never a meters-per-pixel value. m/px is a fact about the
scanner and rots on a rescan; the multiple is a fact about the printed sheet. A
hand-computed m/px prior for these very sheets failed because its assumed dpi
was 18% wrong.

The window is re-centered, not widened. The same ±10% applies, and nothing
searches over scales. Only named pages are affected and they're excluded from
the pass-1 median. **Don't reach for this to make a stubborn sheet fit.** If a
sheet needs it and the printed scale doesn't say so, the fit is the problem.

### Models

Escalation is the only opt-in budget spend left in a place run. Leave it off
for a first volume. Reasoning effort sits beside the model, not in its name,
and is taken by `codex:`, `opencode:`, and `openai-api:`:

```toml
annotation_model = "codex:gpt-5.6-terra"
annotation_variant = "high"
escalation_models = ["codex:gpt-5.6-terra", "codex:gpt-5.6-sol"]
escalation_variants = ["high", "high"]     # one per tier; "" for provider default
```

The same keys work in a volume table and replace the city value there. Caches
are keyed by model plus variant, so changing either creates a new read.

A provider-qualified OpenCode model keeps OpenCode's namespace
(`opencode:openai/gpt-5.6-terra`). Qualify any new backend against fixtures
before putting it in a city config or a ladder.

**The addresses channel costs no budget** but is still a real decision. It has
no producer: it reads whatever escalation already left in `annotations/`. On a
page the ladder never escalated it abstains and the sheet stays flagged, which
is the product promise rather than a fault. It's also the only channel allowed
to refute, so declare the address era first.

## 5. Aliases

Historical names that differ from modern ones live in
`<aliases_dir>/aliases-<volume-id>.json`, volume-scoped, because a rename valid
in 1905 may be wrong for 1950. `docs/INTERNALS.md` has the table rules,
`docs/OPERATIONS.md` the sweep that writes them.

You don't have to guess whether a volume needs one. Matching records the share
of reads that resolve in `work/<volume>/name-match.json`, and the report prints
an advisory note when a volume looks alias-starved. Confirm across the corpus:

```sh
uv run python scripts/audit_alias_coverage.py \
    --city configs/<city>.toml --work work --out work/scratch/alias-coverage.json
```

It also prints each volume's leading unmatched names, which is the shortlist an
alias file is written from. Both bars were measured on one city's corpus, so a
city at a different baseline should treat them as a starting point.

**Check the shortlist for a spelling rule before writing entries.** An alias
table maps one old name to one modern one. If unmatched reads differ from the
modern name the same way every time (a quadrant printed after the street type,
an abbreviation, a punctuation habit) then that is the normalizer's job, and a
table restating it is dead the day the rule lands. Cleveland learned this the
expensive way: 115 generated entries, every one a restatement of a
trailing-quadrant strip, and not one changed a key once the normalizer handled
it. The question is whether the reads name a _different street_ or the same
street spelled differently.

## 6. Optional: a guided story

A story is an ordered set of stops, each a camera position plus an era
selection plus a caption, with its own shareable link. A city declaring no
`[viewer.stories]` gets no story UI. Configuring one doesn't publish it; the
entry list is opt-in per visit, and `docs/OPERATIONS.md` has the URL keys.

```toml
[viewer.stories]
file = "stories/<city>.json"   # sidecar, relative to this TOML's directory
assets = "story-images"        # optional image directory, same base
```

```
story:  id, title, dek?, stops[]
stop:   id                     unique within the story; the permalink key
        title
        body_html?             trusted HTML, one or more paragraphs
        camera                 { center: [lng, lat], zoom, bearing?, pitch? }
        eras?                  ["1910s"]      which chips this stop turns on
        swipe?                 0.0-1.0        fraction of the map's width
        overlay?               { geojson | file, style }  outline on the atlas pane
        media?                 [{ src, alt, caption?, credit?, href? }]
        sources?               [{ label, href? }]
```

`body_html` is trusted HTML, like the credit lines. There's no Markdown
renderer, and adding one would be this project's first non-geographic runtime
dependency. `media.src` is an `https://` URL or a path inside `assets`; local
images are staged as `story-assets/` and travel with the deploy bundle. Prefer
local copies, for the reason the basemap is self-hosted. Story text rides
inside `manifest.site`, so the bundle's leak scan reads every caption.

The config is refused rather than half-rendered. A stop needs an id unique in
its story, a title, and a two-element `camera.center`; `swipe` must be a
fraction; every label in `eras` must name a chip the viewer will show; local
asset paths must exist inside `assets`. Ids are permalink keys, so letters,
digits, `-`, and `_` only.

**The coverage gate.** Before a stop is emitted, the manifest build asserts its
camera center is covered by a served layer in the eras it declares, and logs
the volume that will draw it by title. Presence isn't identity, since the
archives hold specials whose bounding boxes look like ordinary districts, and
the volume envelope isn't coverage, since a volume can publish with a third of
its sheets flagged and the hole still inside the box. Coverage is checked
against placed sheets in `exports/<volume>/gcps/`. It's approximate at the
margins: a sheet's extent is the box of its control points, so it stops short
of the paper's edge, and a volume with no export tree is judged on its envelope
with `[no sheet record]` in the report.

A caption is a claim. Placement accuracy supports block-level statements, not
parcel-level ones, and roughly a third of sheets are flagged rather than
placed.

## 6a. Credits and serving directories

```toml
[viewer]
optional_credits = 'auto-georeferenced by <a href="walkthrough.html">this pipeline</a>'
serving_dirs = ["autogeoref"]         # optional; this is the default
```

`optional_credits` is the site-wide credit line: who georeferenced these
layers. It's HTML and rendered as HTML, so put a link in it. A page saying
"auto-georeferenced" owes the reader somewhere to check the method. The href is
relative because the roots differ: the local server puts the page under
`/viewer/` and a deploy bundle _is_ the web root.

This isn't where the project's own links live. The map page carries a colophon
in its own markup, so every city has it whatever this says. A city setting
nothing publishes no credit line and nothing refuses. The old spelling
`default_credits` is refused by name, since a silently unrecognized key would
publish a site with no credit at all. An `[[viewer.era]]` bucket may override
it for one era.

`serving_dirs` keeps that line honest: a manifest build refuses any
`deploy/tiles/` subdirectory not listed, because every layer it found would
publish under the credit above. **The first entry is your own directory.**
`publish` writes there, `status --city` looks there, and staleness is judged
there.
Later entries are archives you vouch for and never write. A second city on one
host declares its own (`serving_dirs = ["crystal-lake"]`), or its volumes land
unlabeled on the reference city's page.

The check is on the directory, not the layers inside it, because an overview
underlay rides on its parent volume's manifest entry. It matches base name, so
it catches passing the wrong directory rather than a directory named to pass.
Treat it as a mistake-catcher, not a boundary.

## 7. What degrades without which data

| Missing                            | Effect                                                                    |
| ---------------------------------- | ------------------------------------------------------------------------- |
| official centerlines (OSM default) | addresses channel abstains; junction runs on a sparser derived node graph |
| community areas                    | `bounds_areas` unavailable; use `bounds_bbox`/`bounds_from`               |
| rail reference                     | no rail-crossing rescue anchors                                           |
| renumbering table                  | pre-renumbering volumes' addresses channel abstains                       |
| aliases                            | more unmatched labels on old volumes                                      |

Every one is an abstention rather than a guess. Missing data can only drop
acceptance, never silently place a sheet wrong. The one exception is an
undeclared address era, which isn't missing data but a default, and on a
renumbering city's older volume that default actively refutes correct sheets.

## 8. Validate the first volume

1. `autogeoref run <volume-id> --city configs/<city>.toml --work work`. Add
   `--warp` once placements look right.
2. `autogeoref report <volume-id> --work work`. Read the funnel: strict,
   rescued, corroborated, verified, and the flagged list. A suspiciously high
   acceptance rate is a red flag, not a win.
3. `autogeoref review --city configs/<city>.toml --work work`. Optional, and
   worth it on a city's first volume where you're still validating the config
   rather than trusting it.
4. `autogeoref status`. Sheets on disk, funnel, served tiles, provenance.
